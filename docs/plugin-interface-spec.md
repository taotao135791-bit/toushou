# Plugin Interface Specification

**Status:** the single source of truth for what a "plugin" is in OMP GUI: how
packages are installed, what their `package.json` declares, which APIs they can
use, and what they cannot do.

This document describes the **native OMP/Pi runtime package** surface only. GUI
contributions (React code, routes, widgets) are not implemented; the hard
boundary is defined in `extension-host-contract.md`, and the trust boundaries
in `security-model.md`.

## 1. Install sources

The Plugins page accepts a free-form source string (or a folder/file chosen
through the native picker, which becomes a Main-owned grant, never a
renderer-supplied path). Main classifies and, for the current OMP profile,
normalizes the string before shelling out to the runtime CLI
(`src/main/packages.ts`).

### Current OMP profile (`omp plugin install <normalized>`)

Normalization happens in `normalizeOmpPluginSource`:

| Input form | Normalized to | Notes |
|---|---|---|
| `npm:<spec>` | `<spec>` | The `npm:` prefix is legacy Pi notation; OMP takes a plain npm spec. |
| `owner/repo`, `owner/repo#ref` | `github:owner/repo[#ref]` | Bare two-segment names are treated as GitHub references. |
| `git:github.com/owner/repo@ref` | `github:owner/repo#ref` | Legacy Pi GitHub spelling. |
| `https://github.com/owner/repo[.git][#ref]` | `github:owner/repo[#ref]` | Copy-pasted repository root URLs. |
| `https://github.com/owner/repo/tree/<ref>` | `github:owner/repo#<ref>` | Branch/tag picker URLs keep their ref. |
| `https://github.com/owner/repo/blob/...` | **unchanged** (rejected by the runtime) | Deliberate: a `/blob/` URL names a file, not a package root. |
| `/abs/path`, `./rel`, `../rel`, `~` | unchanged | Local paths are passed through untouched. |
| Anything else (`git@host:owner/repo`, non-GitHub git URLs, plain npm names) | unchanged | Forwarded to the runtime as-is. |

### Legacy Pi profile (`pi install <source>`)

No normalization is applied. Consequences:

- GitHub installs require a **full URL** such as
  `https://github.com/owner/repository`; a bare `owner/repo` is classified as
  an npm package name and fails.
- `npm:<spec>`, `git:<url>`, `git@host:owner/repo`, plain npm names, and local
  paths are accepted as documented by upstream Pi.
- The legacy picker also accepts a single `.ts`/`.js` file, which loads as a
  lone extension.

## 2. Package manifest (`package.json`)

A package is a folder with a `package.json`. Fields:

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | Lowercase npm-style name (`name` or `@scope/name`). |
| `version` | yes | Semver `x.y.z`. |
| `description` | recommended | Shown in the package list. |
| `displayName` | optional | Preferred display name in the GUI. |
| `license`, `author` | optional | Ordinary npm metadata. |
| `keywords` | recommended | Include `pi-package` (legacy marketplace discovery); `omp-plugin` marks OMP-native packages. |
| `pi` | see below | Resource declarations for the legacy Pi host. |
| `omp` | see below | Mirror resource declarations for the current OMP host. |
| `files` | recommended | Files to publish, matching the declared resource folders. |
| `peerDependencies` | extensions only | Peer-declare `@mariozechner/pi-coding-agent` (`*`) so the extension resolves pi's bundled core at runtime; never bundle it. |

### Resource declarations

`pi.extensions`, `pi.skills`, `pi.prompts`, and `pi.themes` list files or
directories (glob suffixes are stripped by the GUI's reader). Anything not
declared falls back to the convention directories `extensions/`, `skills/`,
`prompts/`, `themes/` — the GUI always scans both the declared entries and the
convention directory for each resource type.

The `omp` key mirrors the `pi` declarations with the same shape
(`{ extensions: [...], skills: [...], ... }`) so current OMP, which reads its
own manifest key first, recognizes the package. Packages generated by OMP GUI
(scaffold and handwritten "Write plugin") always write both keys; keep them in
sync when editing by hand.

### What the GUI does with the manifest

The GUI **reads but does not validate** installed packages' manifests
(`readManifest` in `src/main/packages.ts`). There is no schema validation:

- an unreadable or invalid `package.json` degrades the listing to convention
  directories and a fallback name derived from the source;
- declared resource paths are contained lexically **and** by `realpath`, so a
  package symlink cannot smuggle resources from outside its own directory.

## 3. Extension API surface

An extension is plain TypeScript loaded by the runtime via jiti (no build
step). Its entry default-exports a factory that receives the runtime's
ExtensionAPI:

```ts
import type { ExtensionAPI } from '@mariozechner/pi-coding-agent'

export default function (pi: ExtensionAPI) {
  pi.registerCommand('my-command', { /* ... */ })
  pi.on('tool_call', async (event, ctx) => { /* ... */ })
}
```

Through the runtime, a package may contribute:

- **extensions** — slash commands, event handlers, tools, UI requests;
- **skills** — `skills/<name>/SKILL.md` with `name`/`description` frontmatter;
- **prompts** — `prompts/<name>.md` templates, surfaced as slash commands;
- **themes** — JSON theme files.

The full upstream API belongs to the runtime, not to OMP GUI.

## 4. GUI bridge (`extension_ui_request`)

A native package's only GUI bridge is the bounded `extension_ui_request` RPC
protocol. The host implements exactly:

| Method | Host behavior |
|---|---|
| `select` | Modal choice list. |
| `confirm` | Modal confirmation. |
| `input` | Single-line modal text input. |
| `editor` | Multiline modal editor, optionally prefilled. |
| `cancel` | Dismisses the matching pending request. |
| `notify` | Bounded system message in the transcript. |
| `open_url` | User-mediated external link; the extension cannot open a browser itself. |

`setStatus`, `setWidget`, `setTitle`, `set_editor_text`, and any unknown method
are **not** implemented; the host emits one visible diagnostic per unsupported
method per session and never fabricates a response.

Limits: at most 20 unresolved interactive dialogs per session; ids are bounded
to 200 characters, titles to 2,000, option lists to 100, and timeouts to 24
hours. The authoritative contract, response shapes, URL rules, and ownership
rules are in `extension-host-contract.md`.

## 5. Known limitations

- **No npm dependencies.** A package cannot declare or install npm
  dependencies; runtimes bundle their core packages and extensions must
  peer-declare them.
- **Link is a symlink.** "Save & sync" / `plugin link` on current OMP creates a
  symlink to the managed source folder for fast edit cycles; the source of
  truth stays in the app-owned directory.
- **New session or reload required.** Installs, syncs, enable/disable, and
  removals take effect in a new chat session or after a runtime reload — never
  retroactively in a running session.
- **Install is trust.** Plugin code runs in the external agent runtime process
  with the runtime's own permissions (filesystem, network, shell — whatever the
  session's permission mode allows). The only gate is the Main-owned native
  confirmation dialog before install/update (`confirmPackageAction` in
  `src/main/ipc.ts`). Installing a package never grants code access to the
  renderer, `window.electronAPI`, Electron APIs, or app routes.

## 6. Where the code lives

| Concern | Location |
|---|---|
| Source classification, normalization, manifest reading | `src/main/packages.ts` |
| Install/remove/update/enable dispatch + confirmation dialog | `src/main/ipc.ts` |
| Scaffolded package template (`pi` + `omp` keys) | `src/shared/pluginScaffold.ts` |
| Handwritten ("Write plugin") managed packages | `src/main/managedPlugins.ts` |
| `extension_ui_request` handling | `src/main/omp/`, see `extension-host-contract.md` |
